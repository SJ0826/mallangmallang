# PR 전략

[브랜치 전략](./BRANCHING.md)과 짝을 이룬다. `main`에 변경을 반영하는 유일한 경로는 PR이다.

## 기본 규칙

- **타깃 브랜치**: 항상 `main`
- **머지 방식**: Squash and merge (히스토리 1커밋으로 압축)
- **머지 후**: 작업 브랜치는 로컬·원격에서 삭제
- **PR 작성자**: 1인 개발이므로 모든 PR은 본인이 작성
- **리뷰어**: 지정하지 않음 (GitHub 정책상 본인을 리뷰어로 지정 불가, 1인이라 의미 없음)
- **Assignee**: 본인(`SJ0826`)으로 자동 지정 — 대시보드 트래킹용
- **라벨**: 작업 성격에 따라 **반드시 1개 부여** (`FEAT` / `FIX` / `CHORE`)

## 라벨 규칙

| 라벨 | 색 | 적용 대상 브랜치 prefix |
|------|----|---------------------|
| `FEAT` | 진녹색 (#822333) | `feat/*` |
| `FIX` | 진녹색 (#193701) | `fix/*` |
| `CHORE` | 밝은 녹색 (#3eb32f) | `chore/*`, `docs/*`, `refactor/*`, `release/*` |

> 한 PR에 여러 성격이 섞이면 가장 큰 비중의 라벨 1개를 선택. 라벨이 모호하면 PR을 분리하는 게 좋다.

## PR 제목 컨벤션

커밋 컨벤션과 동일한 prefix를 사용한다. Squash merge하면 PR 제목이 그대로 main 히스토리에 남기 때문에 중요.

```
feat: 캐릭터 변형 스프링 물리 적용
fix: iOS 햅틱이 첫 탭에서 무시되는 문제 해결
chore: granite 1.0.27 → 1.0.28 업그레이드
docs: README 시작하기 섹션 보강
refactor: 캐릭터 상태를 store로 분리
```

## PR 본문 템플릿

```markdown
## Summary
- 무엇이 바뀌었는지 불릿으로 (파일 경로/심볼 단위)

## Why
- 이 변경이 필요한 이유 / 의사결정 맥락
- 외부 의존(콘솔 설정 변경, 라이브러리 메이저 업 등) 있으면 명시

## Test plan
- [ ] 검증한(또는 검증할) 항목들
- [ ] 샌드박스 앱에서 확인이 필요한 시나리오
```

1인 개발이라 리뷰어용 설명이 아니라 **6개월 뒤의 본인이 빠르게 맥락을 복원할 수 있게** 적는다.

## 생성 시점 가이드

PR은 다음 시점에 만든다:

1. **의미 있는 작업 단위가 끝나고 다음 작업이 성격이 다를 때** (한 PR에 무관한 변경 섞는 것을 방지)
2. **배포·태깅 직전** (`.ait` 빌드해서 콘솔 업로드 전)
3. **위험한 변경 머지 직전** (Granite/RN 메이저 업그레이드, `granite.config.ts` 구조 변경 등)
4. **브랜치가 main에서 5커밋 이상 벌어졌을 때** (충돌·롤백 비용 감소)

자제할 시점:
- 같은 주제 작업이 진행 중일 때 (커밋만 쌓고 PR은 마지막에)
- typo·메모만 수정한 마이크로 변경 (PR은 만들되 능동적으로 권유하지는 않음)

## 머지 후 정리

```bash
git checkout main && git pull
git branch -d <merged-branch>
# 원격 브랜치는 GitHub UI "Delete branch" 버튼으로 삭제
```
